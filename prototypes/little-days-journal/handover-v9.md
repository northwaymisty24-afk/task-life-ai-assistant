# 小日子 H5 前端交接说明

本文给接手这个页面的人（或 AI）。范围只限 A 侧的 H5 原型 `little-days-h5.html`，不覆盖后端、解析器和公众号接入。

- 项目：连接任务与生活的 AI 个人助手，南京大学学生团队，开发期 2026-11-15 至 12-04。
- 文档基线：`docs/PRD_v0.7.docx`（产品，以此为准）、`docs/MVP_SPEC_v1.0.docx`（技术）。**两者冲突时，用户可见行为按 PRD。** 产品负责人已明确「范围以 PRD 为准」。
- 本文写于 2026-11-25，对应页面版本：存储键 `little-days-prototype-v9`。

## 1. 这个文件是什么

单个 HTML 文件，约 312 KB，打开即用（插画是内嵌的，体积主要在这里）。

- 无构建步骤、无外部请求。字体、插画、图标全部内嵌（base64 / data URI），断网也能完整显示。
- 数据是**示例数据**，存在浏览器 `localStorage`（键 `little-days-prototype-v9`，读写都包了 try/catch）。换一台设备、换一个浏览器，数据不互通。
- 路由用 `location.hash`，五个栏目：`#tasks`（可带日期或 `week`/`month`）、`#habits`、`#chat`、`#diary`、`#insights`（可带标签，如 `#insights/做事方法`）。日记有三条路由：`#diary`（今天）、`#diary/night`（今天，安排明天默认展开，公众号晚间消息的深链接用这个）、`#diary/week[/日期]`（这周）。旧的 `#review` 会自动跳到 `#diary/week`。
- **没有接任何后端接口。**`/api/v1/turns`、`/api/v1/tasks`、`/api/v1/corrections` 都还没调用。

### 改这个文件时必须守住的三件事

1. **保存不要改回表单提交。** 所有保存都走按钮 click（`#save-task`、`[data-submit="chat-form"]`、`[data-submit="diary-form"]`、`#add-habit`），表单的 `submit` 事件只作为回车键的兜底。原因：在受限的 iframe 预览里（比如聊天工具的文件预览框）表单提交会被拦截，按钮点击不会。用 `type="submit"` 会让保存在预览环境里完全失效，这个坑踩过一次。
2. **`<dialog>` 是模态的。** 事项详情打开时会挡住页面其他点击。写自动化测试时记得先 `Escape` 关闭，否则后续所有点击都会打在遮罩上（这个坑也踩过）。
3. **动效要留 `prefers-reduced-motion` 分支**，交互元素要留 `:focus-visible`，触控目标不小于 44px。现有代码都满足，改动时别破坏。

## 2. 视觉系统

目标风格：苹果式的简洁克制 + 童趣温馨 + 手作朴拙感（参考喜茶的简洁童趣）。不要 AI 生成器那种机械感图标和渐变。

### 字体

- 标题、导航、品牌名用 `--display`，即 **LD Round**。它是寒蝉半圆体（ChillRoundM）的子集，只截取了用到的字，14 KB，内嵌为 woff2。
- **字体许可：SIL OFL 1.1。协议要求修改版（含子集）必须改名，所以叫 LD Round，不能叫回寒蝉。** 加新标题文案时如果出现方块字，是子集里没有这个字，需要重新截取——原字体包 `@proj-airi/font-chillroundm`。
- 正文沿用系统字体栈（PingFang SC / 微软雅黑 / Noto Sans CJK）。不要把正文也换成圆体，会糊。

### 颜色

CSS 变量集中在 `:root`，禁止在规则里写死颜色值。主要几个：

```
--paper #faf7f2   纸底      --forest #365745  主绿
--white #fffdfa   卡片      --peach  #f3ddd1  插画底
--ink   #252e28   正文      --rust   #884b37  警示
--butter #f4dc96  胶带      --night  #3d3866  夜色
--paper-note #fffcf4  便签  --rod    #dcc6a2  卷轴木杆
```

四象限各有一组标签色（`.q1`–`.q4`），提醒状态三色（`.sent-待发送` / `.sent-已发送` / `.sent-未能发送`）。

整页叠了一层 SVG 噪点（`--grain`）做纸张纹理，强度很低，不要加重。

### 图标

导航图标是手绘线条风，不是通用图标库那种。每个都用 rough.js 做过一次轻微抖动（roughness 0.5），所以线条不是数学直线。

| 页面 | 图标 |

| 待办 | 打了勾的台历 |
| 习惯 | 发芽的小苗（产品负责人指定） |
| 聊天 | 三点气泡 |

| 周回顾 | 柱状图加一颗星 |

加新图标要配套：先画干净的 SVG 路径，再过一遍 rough.js，保持线宽 1.5–1.6、圆端点圆接头。源文件和脚本见「资源怎么来的」。

### 插画

**四张都是产品负责人提供的手绘稿**，不是代码画的，不要再用 SVG 滤镜重做。统一处理成 700px 宽的 WebP 内嵌（base64），每张 18–30 KB。一页只放一张，固定在右栏。

## 3. 各页面的交互决定

### 待办

#### 日期导航（改过一次，别改回去）

原来是 `‹ 周简表 月简表 ›`，两个箭头夹着两个视图按钮。产品负责人的反馈是"乍一看不清楚它们管什么"——因为箭头紧挨着视图按钮，看起来像在翻视图，实际翻的是周。

现在拆成两组：**左边是"看哪一周"**（`‹ 上周　11月23日–11月29日　下周 ›`，箭头贴着日期范围，桌面端带文字，窄屏只留箭头），**右边是"用哪种视图"**（周简表 / 月简表）。月视图下文案自动变成"上月 / 下月"。

跳到不是今天的那一周（或月视图跳到别的月）时，日期旁边多一个虚线框的 **↩ 回到今天**；回到当前就自动消失。判断条件在 `calendar()` 里的 `away`，三种视图各判各的，不要合并成一个。

- 顶部日期条，可切周简表 / 月简表。
- 当天分两组：**有具体时间**、**未定具体时间**。每条标明是执行、截止还是提醒，三者标签不同（PRD 5.1 的要求）。
- 右栏「本周重点」= 四象限里「重要且紧急」且本周未完成的，**最多列 10 条**。
- 提醒状态标签：待发送 / 已发送 / 未能发送。示例数据里「取快递」那条是未能发送。

### 事项详情（模态弹窗）

字段顺序固定，不要调换：

1. 事项名称
2. **执行时间**（日期 + 时间）——排在前面是有意的：先定什么时候做，这样每天才能排成一段一段的时间表
3. **截止时间**（截止日期 + 截止时刻）——和执行**分开存**，不能合并
4. 提醒（频率 → 提醒日期时间 → 「没做完就隔一会儿再提醒」+ 间隔 → 额度提示 → 当前发送状态）
5. 四象限（手动选，不自动判定）
6. **任务步骤与进展**（见下）
7. 查看来源原话

校验：填了执行时间必须有执行日期；填了截止时刻必须有截止日期。

**为什么一定要分开这两个时间**，目的有两条，缺一条这个设计就没意义了：

1. **让用户对 DDL 有清楚的意识** —— 哪天必须交，是个硬边界。
2. **让每天的安排能排成一段一段的时间表** —— 什么时候做，是可以挪动的。

合并成一个时间字段，这两件事就都丢了。PRD 3.3 也明确要求「任务最终截止、步骤截止、计划开始和提醒发送时间分别记录」，并且「日期无确切时刻时保留日期精度」。

**对话里的追问规则**：先问执行时间。用户没主动说截止的时候，把「有没有一定要交的日子」和「需要我什么时候提醒你」**合并成一次追问**，问到了就记上去。不要拆成两条消息连着问——PRD 2.4 规定存疑项合并确认，并明确禁止逐条发确认卡片、禁止要求用户对每条分别回复。

### 任务步骤与进展（这一块的逻辑要理解清楚）

产品负责人的判断是「进展基本等同于任务步骤」。界面上按这个来，数据上仍然分开。

界面上是一块，数据上是两张表。

- 上半是**步骤**：可勾的复选框，可增删。
- 下半是**进展**：从公众号或聊天来的进度，按日期排，**只读，没有手动添加入口**（手动输入框已删除）。

规则：对话里说的进度，能对上某一步就勾掉那一步；比一步更小、还没勾掉任何一步的，就只留一条进展，当天的回顾里也看得到。跨天的进展全部保留，步骤勾完了也不消失。

**为什么数据上要分开**：PRD 3.4 规定「进展不改变任务的 status」，9.2 要求「开头改好了不能代表整篇完成」。如果进展直接写成步骤，解析器每识别一句进度就得决定「这是哪一步」，判断错就会误勾——而误标完成是 PRD 7.1 的红线。分开存，匹配得上就勾，匹配不上只留进展，红线就踩不到。

### 习惯

- 进行中**最多三项**（PRD 3.5）。满了添加框禁用并说明原因。
- **列表行只有两个东西：左边一个圆圈（点一次＝记一次），右边一整块可点的正文。** 正文显示名字、非进行中时的状态小标签、频率、上次记录；只有填过最小版本的那一项，才在后面追一句「最小版本：…」。
- 改名、状态、最小版本、历史记录**全部收进弹窗**（点正文打开，`#habit-editor`）。

**这一版为什么把行改简单了**：上一版每一行都挂着一个「最小版本」输入框和一个状态下拉，结果是——用户不知道为什么每条进行中的习惯都要先想一个「缩小后的版本」，也不知道那个下拉和减量卡里的「缩小目标」是什么关系。**缩小是遇到困难时才做的事，不是建立习惯时就要填的字段**，所以它只在弹窗里出现，列表上只在填过之后才显示结果。**不要把输入框和下拉放回列表行。**

弹窗里的状态是三选一的单选块，每一项下面有一句解释（谁来设、提不提醒），这是因为产品负责人反馈「暂停 / 休眠 / 放下看不出区别」。解释文案就是那三行小字，不要删。

四个状态的分工（PRD 3.5：首版自动实现的只有「进行中转休眠」，其余手动）：

| 状态 | 谁设置 | 含义 | 提醒 |
|---|---|---|---|
| 进行中 | 用户 | 正在做 | 提醒 |
| 休眠 | **系统自动** | 连续 7 天没记录，静默折叠 | 不提醒、不显示断签 |
| 暂停 | 用户 | 先停一阵，之后还捡起来 | 不提醒 |
| 放下 | 用户 | 结束了 | 不提醒 |

休眠在界面上表现为名字旁一个「休眠中」小标签，下面写「这段时间没有记录，已经不再提醒」。下次打卡自动消失。**休眠的习惯仍然占三项名额**（PRD 要求同时进行中不超过三项），腾位置靠下面的减量卡。

**减量卡**：两项以上进行中的习惯连续 7 天没记录时出现，当天只出现一次。三个选项，**顺序固定不可改**：

> 缩小目标 / 先只留最想做的一两项 / 保持不变

「缩小目标」**打开第一个休眠习惯的弹窗并把光标落在最小版本输入框上**（上一版是聚焦列表里的输入框，那个输入框已经删了）；「先只留最想做的一两项」把其余休眠项转为暂停；「保持不变」关掉。

这个顺序是 PRD 6.4 的落点：《老子》「少则得，多则惑」**不作为引文出现在产品里**，只落实成「缩小排在保持之前」这个默认排序。**不要加劝诫文案**（详见第 4 节红线）。

### 聊天

- 顶部小狗按时段打招呼（凌晨 / 早 / 午 / 下午 / 晚各一句）。
- **输入框上方的四个快捷开头（记一件事 / 这件卡住了 / 随便说说 / 经验总结）已经删掉了。** 理由是产品负责人的判断：接上模型之后这几类本来就能自动识别，按钮只是把输入框填一半，点下去什么也没发生，像坏的。**不要加回来**，也不要换成别的 chips。
- 每条用户消息下方有小字：转成待办、留进日记（已留过则变成「在日记里查看」）、收进经验本。
- 右栏一张贴胶带的便签「今天留下的话」，显示今天最新留下的一句和条数，右下角一行小字「在日记里看」。
- **示例回复的行为**：发一句不带时间的任务 → 回「记下了。打算什么时候做？有没有一定要交的日子？要的话我在之前提醒你一次。」带了时间就不追问。接上模型后由教练模块来问，判断条件可以照这个来。

#### 聊天里怎么收进经验本（不弹窗，在对话里完成）

产品负责人的反馈：聊天里又要划词、又要在弹窗里填"想让助手整理哪部分"，太绕。现在整条路都在对话里走完：

1. 点消息下面的「收进经验本」→ 助手在对话里回一句：**「好。你可以在那段话里划出要收的部分，或者直接跟我说想整理哪一部分，我整理完就收进经验本。」** 那条消息加一圈绿框，下面出现**一个按钮和一个 ×**。
2. 用户有两条路，**两条都通**：
   - 在那条消息上**直接划词**（原生选择，手机长按即可）。划之前按钮是「收整段」，划了之后变成「收划出的 N 字」。
   - 或者**直接在输入框里说**「只整理跟朋友聊完那部分」。处于挑段状态时，发出去的这句话不走正常回复，而是当成整理要求。
3. 助手整理出标题和正文，**直接存进经验本**，然后在对话里回执：「收好了。标题我拟的是「…」，正文：…」，这条回执下面挂三个小字：去经验本看看 / 加标签 / 撤销。

几条别改坏的：

- **那个按钮只写它当下会做的事**：没划选时「收整段」，划了就「收划出的 N 字」，跟着选区实时变。不要写成「整段都收」这类固定文案——绿框本身已经在说"这段可以划"，一个固定标签会和它打架，让人以为只能整段收。
- 旁边是一个 **×**，不是「算了」两个字。退出这件事不该和"收进去"一样重：× 小、不抢眼，但必须留着——处于挑段状态时输入框发出去的话会被当成整理要求，没有出口的话，改主意的人随手打一句就会莫名其妙多出一条经验。按 × 之后助手在对话里回一句「好，那这段先不收」，让这段对话读起来是完整的。
- **这里没有"用这版 / 用原话"**。弹窗里有是因为那是一次性的决定；在对话里，不满意就按「撤销」再说一次，比在聊天里塞一个双选开关自然。
- 「撤销」把经验条目和那条回执一起删掉（`data-unpin`），**原话留在日记片段里**。
- 挑段状态是内存变量 `picking` / `pickSel`，不进 `state`，刷新就没了——它是一次交互的中间态，不该持久化。
- 助手问的那句和回执**是真消息，进 `state.chat`**，所以回头翻聊天记录能看到"这条经验是怎么来的"。这是故意的，别改成浮层提示。
- 弹窗（`#pin-sheet`）现在只服务三个入口：今日回顾/周回顾里的原话、「此刻的感受」的建议卡、经验本「＋ 写一条」。聊天不再用它。

### 日记（今天 / 这周）

**为什么周回顾和晚间日记合并、为什么晚间日记不再单独占一栏**：这是从头切了一遍得出的。用户在这个产品里只有三个动作——说（聊天）、做（待办、习惯）、回看。原来的六栏里，回看被按时间跨度切成三份（今日在晚间日记里、本周在周回顾、跨期在经验本），而晚间日记本身是"回看 + 说 + 做"的混合体。

两条判断：

1. **仪式感来自触发，不来自导航位置。** 晚间收尾最大的敌人是用户晚上忘了打开，这只能靠公众号在固定时间推一条消息解决；用户顺着消息点进来，不关心落地页是导航第几项。PRD 6.2 和 2.5 写的也是公众号发起对话，H5 那一页是"想看全的时候点进去"。
2. **周回顾一周用一次，不该占常驻导航位。** 按使用频率：待办和聊天每天多次，习惯和回看今天每天一次，周回顾每周一次。

所以日记是一栏，里面用标签页切今天和这周。经验本保留独立一栏（产品负责人的决定），理由是它按主题检索，和按日期回看是两种组织原则。

手机底栏五项，每项 74px，比六项的 62px 舒服。

#### 今天

顺序：今日回顾 → 此刻的感受 → 安排明天 → 保存。

**今日回顾**放在最前面，形态是：

1. 一排小标签：几件完成、几条进展、几句留下的话。
2. 一段**总结成整段的文字**（不是一个个小卡片），可点击。
3. 点开像竖着的卷轴向下展开（上下两根木杆 + 纸面），里面按时间列出：几点勾掉了什么、几点记了什么进展、几点说了什么（用原话）。
4. 卷轴末尾是小狗的鼓励，按日期轮换，**符合当天上下文**。
5. 当天还有没完成的事时，鼓励后面多一句「……今天还没完成。想聊聊卡在哪一步吗？」加一个「去聊聊」，点了带着这件事跳到聊天。**全部完成时这句不出现。**

白天留下的长段想法**不单独再列一遍**——卷轴展开里本来就有完整原话，重复了（这是删掉过一次的）。

「此刻的感受」是今晚新写的话。

**「安排明天」默认折叠**，标题右边是「展开/收起」。傍晚 17 点以后、或从 `#diary/night` 进来时默认展开。白天收起时显示一行「明天已经排了 N 件事。晚上再来安排也可以」。折叠状态下 `note` 字段不在 DOM 里，`readNightDraft` 用 `?? state.nightDraft.note` 兜底，**改这块时不要把兜底去掉**，否则白天保存会把备注清空。「安排明天」可以拖动排序，标题右边除了「＋ 添加明日事项」还有「去聊天里说」——用对话录入比填表单快，点了带上下文跳到聊天并预填「明天我想」。这是功能性跳转，不是导航卡片，和之前删掉的那几张不一样。

#### 这周

三张卡：

1. 这一周完成的事项（柱状图，周一到周日）
2. **这周有没有一点时间留给自己** —— 先一行「这周为自己留的习惯：背单词 2 次」，再按日期列生活片段的原话。习惯算在这里，因为习惯是为自己做的，不是别人交代的任务。两样都少时才说「这周留下的生活片段不多」，然后邀请一句，**不作生活质量判断**。
3. 这周留下的话（原话按日期并置，每条带「收进经验本」）

上一周/下一周用右上角的箭头，路由是 `#diary/week/<日期>`。

### 选周日历（日记 · 这周顶部）

原来是页头两个小箭头，一次只能挪一周。产品负责人的反馈是"太小太边缘，跨几周要一直点"。现在换成**一个月一屏的日历**（`weekPicker`）：七列是周一到周日，**一行就是一周，点一行换那一周**，当前选中的那周整行高亮，今天那一格是实心的。行尾直接挂徽章和完成数——所以"看哪一周"和"哪一周过得怎么样"是同一个视图，不用先翻再看。

- `‹ 上月 / 下月 ›` 翻月。翻月会选中那个月 1 号所在的那一周（`moveMonth` 返回的是当月 1 号），所以翻过去就有东西看，不用再点一次。
- 选中的周不含今天时，月份旁边出现 **↩ 回到这一周**。
- 下面的卡片标题跟着变：当前周是「这一周完成的事项」，别的周是「11月9日–11月15日完成的事项」；「这周有没有…」「这周留下的话」在看别的周时变成「那一周…」。页头副标题写清楚是哪一周、离现在几周（「11月9日–11月15日 · 2 周前」）。
- 原来那张「往前几周」列表卡**已经删掉**：日历已经能跳任意一周，列表是重复的。

两个手绘徽章（`icon("crown")` / `icon("rose")`，生成方式见第 8 节）：

| 徽章 | 条件 | 含义 |
|---|---|---|
| 黄色小皇冠 | 这一周"完成了事"和"为自己留了时间"两样都不为零 | 两头都顾上了 |
| 彩色玫瑰 | 完成率 > 80% | 这一周做完了绝大部分 |

完成率 = 这一周所有落在某天上的事项里完成了的比例（`weekStats()` 里按 `onDay` × `taskDone` 逐天数，和周简表的口径一致）。当前这一周的徽章显示在「这一周完成的事项」标题旁。

**不要把徽章做成可点的、或者做成成就系统**。它只是一个看得见的肯定，没有积分、没有连续天数、没有"打破纪录"。PRD 6.4 的红线：不激励、不比较、不制造亏欠感。同理，没拿到徽章的那一周不要显示任何"差一点"的提示。

示例数据里特意铺了两周：上一周 4 项全完成且有习惯打卡和生活片段（皇冠 + 玫瑰），上上周 1/3 完成且没有为自己留时间（没有徽章）。**改 seed 时别把这两周删了**，否则日历上一个徽章都看不到。

### 拖动排序（日记「安排明天」和待办共用一套）

手柄是一只小手，鼠标移上去变抓手。**上下箭头已删除**（多此一举）。键盘用户选中手柄后按上下方向键也能调序——这是无障碍规范对拖拽的要求，不占视觉空间，不要删。

一套代码管两处：每个可拖的卡片是 `.plan-item[data-plan-id][data-order-key]`，`moveOrder(key,from,to)` 按 key 写回不同的地方——

- `tomorrow` → `state.nightDraft.order`（跟着今晚回顾一起保存）
- `day:YYYY-MM-DD` → `state.dayOrder[日期]`（待办页按天记，立刻生效）

**只在同一个 key 的列表内部允许落点**（`pointermove` 里比对 `orderKey`），否则会出现把待办卡片拖进明日清单这种事。

待办页默认按「有具体时间 / 未定具体时间」两组排。**用户一旦拖过，这一天就改成单组「按你排的顺序」**，和明日清单的行为一致——人工排过的顺序优先于系统分组。明天那一天如果今晚回顾里已经排过，待办页直接沿用（`dayOrderFor()` 的兜底顺序：当天自己的 → 今晚回顾的 → 空）。

### 经验本

交付延到 12-20 之后加做的，已经实现。它不是"另一种记录类型"，是**从日记里钉出来的那几句**。

**为什么不让用户选"这是日记还是经验"**：讨论时举的例子是「我发现我上午很专注，下午到晚上精神就涣散」——它同时是今天的观察、一条自己的规律、一条画像材料。连我们都划不清的边界，不能丢给用户。所以改成问一个他本来就会回答的问题：**这句话以后还想再看到吗？**想，就钉；不想，它仍然在那天的日记里。

- 原话只有一份，存在日记片段层。经验条目只引用（`sourceId`），**不复制、不改写**。
- 收录动作叫「收进经验本」，在所有能看到原话的地方长得一模一样：聊天消息下、今日回顾卷轴展开后的每条说过的话、周回顾「这周留下的话」。已经收过的不再显示这个按钮。
- 聊天里那条消息如果还没成为日记片段，点收录会**先把它存成日记片段再钉**——因为感想本来就该默认留存，收录是另一个独立动作。

**收录弹出表**（底部弹出，手机上贴底）：

1. 原话可划选。划了就只收这一段，不划收整句，旁边有「用整句」退回。**原话永远不被改写**（PRD 3.9：感想的原话字段不得被任何概括字段覆盖）。
2. **助手整理块**：一个标题 + 一段正文，都是助手按划选到的原话整理出来的，**两个框都能直接改**。上面一对按钮「用这版 / 用原话」——选「用原话」就把正文换回逐字原话、标题换成第一个短句。默认是「用这版」。用户动过标题或正文之后，再改划选范围**不会**冲掉他写的。
3. 标签：下拉里选，**每条最多两个，整个标签库最多十个**。新建标签要在下拉里选「＋ 新建一个标签」才会出现输入框；库满了就没有这一项。
5. 「想记住的话」右上角的麦克风只是说明入口，不录音（理由见上面的改动清单）。
4. 「让助手参考这条」开关，默认关。

**上一版的「一句话记住它」已经删掉**，换成了上面这个标题＋正文。产品负责人的原话是：一般就是划录原文收录，然后默认 AI 总结整理，有按钮决定是否采用 AI 改的内容，带标题，同时可以直接编辑。所以这里的默认值是「采用」，拒绝的成本只有一次点击；不要改成默认不采用，也不要把它做成不可编辑的只读结果。

**`tidy()` 是本地占位实现**（剥语气词 → 断句 → 取第一句里真正带信息的那个分句做标题）。接后端时把它换成一次模型调用，输入原话、输出标题与正文即可，**调用点和约束都不用动**：原话另存、结果可编辑、可拒绝。

**措辞统一叫「标签」，不叫「主题」。** 旧版那句「用顿号或空格隔开」的提示已删除——分隔符规则是让用户迁就输入框，正确做法是一个一个加成小块。

**标签为什么是自由的、又怎么不失控**：产品负责人要自由多标签，不限于预置那几类。代价是会长出近义标签。这一版把压制办法换成了硬上限，三条都不要拆掉——

- **整个标签库最多 10 个**（`TAG_LIMIT`）。满了之后只能从已有的里面选，这是防近义标签的主力。
- **每条最多选 2 个**（`TAG_PER_NOTE`）。
- 新建要多走一步（下拉里选「＋ 新建一个标签」），让复用比新建顺手。

筛选栏现在把标签全列出来（最多 10 个，列得下），末尾是「管理标签」。上限在 `TAG_LIMIT` / `TAG_PER_NOTE` 两个常量里，要调只改这两处。

**标签管理（`#tag-manager`）**：列出所有在用的标签和用量，每行可以改名或删除。

- **改名改掉所有用到它的条目**（`renameTag`）。改成一个已存在的名字就等于合并，合并后同一条上的重复会自动去掉。
- **删除是把这个标签从所有条目上去掉**（`dropTag`），条目本身留在经验本里。删除走两步：先把那一行换成「从所有条目上去掉「X」？确定去掉 / 算了」。**不要改用 `confirm()`**——受限 iframe 里的原生对话框会被拦掉，用户会以为按钮坏了。
- 标签仍然不单独存，最后一条用它的条目被移走它就消失。

**单条的标签（`#tag-edit`）**：卡片上的标签本身是按钮，点开就能改这一条的标签；没标签的条目显示「＋ 标签」占位。两个弹窗和收录表用的是同一套控件（`renderTagUI(ui, tags)` + `addTagTo(list, raw)`），**加第三处的时候继续复用，不要再抄一份**。

**「让助手参考这条」就是画像确认**。默认关的时候，经验本只是用户自己的笔记，系统不拿它个性化。勾上才等于 PRD 3.8 说的"用户勾选后保存为近期状态"。前端现在只存了 `useForProfile` 这个布尔值，**接后端时要把它落成一条 confirmed 的 profile_item（scope = 近期状态），不能绕过画像的确认流程**——未经确认写入画像是 PRD 7.1 的红线。

**经验本里可以直接写一条**（右上角「＋ 写一条」）。它**复用同一张收录表**，只是把上面的原话区换成一个可写的输入框（`pinMode === "own"`），并且**藏掉「想让助手整理哪部分」那一栏**——自己坐下来写的东西本来就成体系，不需要再挑一段，直接整理即可，那一栏只在从日记/周回顾划选原话时出现。边写边出助手整理的标题和正文，标签、「让助手参考这条」、保存按钮完全一样。上一版是页面里单独一张内嵌表单，字段和弹出表不一致，入口也多一个，已经删掉，**不要再加第二张表**。

保存时会**同时生成一条当天的日记片段**（来源标「网页 · 经验本」），经验条目再引用它。这样 PRD 的可回溯约束不破：任何记录都能查到生成它的原始表达。不要改成凭空新建条目。

**列表卡片**：标题 → 正文（整理过的那段；老数据没有正文就显示原话）→ 标签和日期。原话默认**不显示**，点操作里的「查看原话」才展开。标签是标签形状的按钮，点开能改这一条的标签。**不显示「来自聊天 / 来自日记」**——它不影响任何判断，`via` 字段还在数据里，后端统计来源照用。

**卡片上的操作是滑出来的，不是一排小字。** 三个入口都通向同一个面板：长按卡片 500ms、向左滑超过 40px、点右上角的 `⋯`。面板里三个方框：取消/选择助手参考、查看原话、移出经验本。一次只开一张；点卡片外面、按 Esc、执行完任一操作都会收起。

为什么改：上一版每张卡下面挂三行小字（不再让助手参考 / 看它是哪天记的 / 移出经验本），产品负责人反馈"小字太多"。卡片是用来读的，操作不该一直占着视觉。**`⋯` 那个按钮不要删**——长按和滑动都是指针手势，键盘和读屏用户只有这一个入口（面板关闭时用 `visibility:hidden`，顺带把里面的按钮移出焦点顺序和无障碍树，这是故意的，别换成 `opacity:0`）。

**搜索**：筛选栏上方一个搜索框，匹配标题、正文、原话和标签。它**不重新渲染页面**，只给已经渲染出来的 `.ins` 卡片切 `hidden`（`applyInsQuery()` 读每张卡上的 `data-hay`）——重渲染会让输入框失焦，中文输入法打到一半就断了。改这里务必保持这个做法。

**移出经验本只删条目，原话留在日记里。** 这条要守住。

**两样讨论过但决定不接的**：H5 里不做录音（PRD 1.4 已定语音识别由微信提供，3.1 要求语音文件不落盘、不保留 media_id，为一个整理功能破这条不值得）；不接 ima 一类的外部知识库（多一个外部依赖，而经验本里会有涉及第三人的内容；现有的 OpenAI 兼容接口足够生成标题建议）。模型在这里只许生成标题，不许动原话。

**隐私**：经验本会存「导师周一上午回消息最快」这类关于第三人的内容，试用期开发团队能看到数据库。这一点要写进给试用者的说明。

### 感想、经验总结与日记的归属（跨页面，改过几次，按最终口径执行）

**一、所有感想都要记录，默认留存。** PRD 2.3：要用户回复才能保存感想，视为未达标。3.7：日记片段默认留存，用户主动排除时才关闭，无需逐条选私密。**接上解析器后，聊天里说的感受应当自动成为日记片段，不需要用户点任何按钮。**

**二、「留进日记」按钮是补漏，不是主路径。** 它的定位是收解析器漏掉的话。接解析器时要同时补一个「这句别记」，对应 PRD 3.7 的口径：「不放待办」保留合格的日记原话，「这句别记」按显式不留存或删除处理。现在原型没有解析能力，按钮先照旧保留。

**三、短碎碎念和大段经验走同一条入口，但归属不同。** 这是产品负责人对上一条的补充：

- **短的即时感受**（针对任务的一两句）：留在当天的日记片段里，汇进今日回顾那段总结。
- **大段的经验总结、抽象感悟**：**转存到晚间日记**，作为类似「此刻的感受」那样的整体性抽象回顾来看，而不是散成一条条流水。

**四、「转存到晚间日记」现在是怎么落地的。** 今日回顾的卷轴展开后，长段原话是**完整显示**的——不截断、不改写、不打情绪标签。所以它已经在晚间日记里了。

曾经另做过一块「白天你写下的想法」，单独列在「此刻的感受」上方，后来**删掉了**，因为和卷轴重复。**不要再加回来。** 如果要强化这一块，正确方向是在卷轴内部把长段内容做视觉区分（比如单独的引文块、和事件行分开），而不是在卷轴外面再列一遍。

**五、聊天里的「经验总结」快捷开头**（填入「今天我发现：」）是长内容的入口之一；另一条是任何原话旁边的「收进经验本」。

**六、经验本已经做了**，见上一小节。原提案 `docs/insight-notes-v2.md` 里的分类方案（固定五类 topic）**已被推翻**，改成自由多标签；"首版不做"那段也已过时（交付延到 12-20）。那份文件现在只作为讨论留档，实现以本文为准。

**七、「此刻的感受」保存后先问一句，不直接给总结。** 顺序是产品负责人定的，三步，别压成一步：

1. **问**：保存今晚回顾之后，「此刻的感受」下面出现一张卡，只问「这段里有想收进经验本的吗？」，两个按钮——「有，我来挑一段」「这次没有」。**这一步不展示任何整理结果**。点「这次没有」这段就不再问（记在 `state.pinSkipped`，改了内容会重新问）。
2. **挑**：点「有」打开收录表，整段原话在里面，用户**划选那一段**，或者在「想让助手整理哪部分？」里一句话说清楚（例如"只留做事方法那一段"），按「重新整理」。
3. **整理**：这时才出标题 + 正文，配「用这版 / 用原话」，两个框都能改。

为什么不能省掉第一步：先甩一段 AI 总结出来，等于默认用户要收录、也默认助手的切分是对的。先问一句，用户才有机会说"不是这段"。

**只建议，不自动存**——PRD 3.8：画像和经验都要用户确认过才算数。**公众号侧走同一条流程**：用户说完一段，助手回一句「有要收进经验本的吗」，用户说有，再让他说要整理哪部分（微信里划词不方便，就靠对话说），然后把整理结果发回去等确认。**不要做成后台静默收录**，也不要在用户还没确认时就写画像。

前端的 `tidy(text, hint)` 是占位：`hint` 为空就整段整理，有 `hint` 就按关键词挑句。接后端时整个函数换成一次模型调用，`hint` 直接当作给模型的指令，**调用点和约束不用动**。门槛也别去掉：**没有感受内容、或内容短于 12 个字时不弹这张卡**。

## 4. 不可违反的产品红线

全部来自 PRD 7.1，触发任何一条都会阻断验收。改文案时逐条对照。

1. **不得出现断签、连续打卡天数、「完成率低于预期」一类评价性文案。** 完成任务数等客观统计可以保留。
2. **不得评价用户是否贪多、能力如何。** 具体到鼓励语：不能说「暂时落后」「你可能要调整状态了」「是不是贪多了」「合理评估一下自己的能力」。「落后」本身预设了一个标准，也不行。只陈述事实：「『核对参考文献』有了着落，你也把当时的感受说出来了。」
3. **不得用系统生成的情绪标签或情绪曲线替代用户原话。** 用户自己用的情绪词照原样保留。
4. 不得误标整项完成（见第 3 节进展与步骤）。
5. 不得未经用户确认写入画像。
6. 被用户排除的内容（`include_in_review = false`）不得直接或间接进入回顾与画像。

另有一条产品口径，实现时容易弄反：**感想默认留存，不需要用户确认。** PRD 2.3 写明「如果要用户回复才能保存感想，视为未达标」，3.7 规定日记片段默认留存。现在页面上的「留进日记」按钮只是补漏（收解析器漏掉的话），接上解析器后感受应当自动进日记，另外补一个「这句别记」。

## 5. 前端当前的数据结构

全部在 `state` 对象里，仅供本地示例，字段名尽量贴着 PRD 第 3 节。接后端时以 `contracts/openapi.yaml` 为准。

```
state.tasks[]    id title
                 date time            执行（PRD: 计划执行时段）
                 dueDate dueTime      截止（PRD 3.3 due_at）
                 repeat               ""|once|daily|weekly|monthly
                 reminderDate reminderTime repeatWeekday repeatMonthday
                 remindEvery          持续提醒间隔（分钟），"" 为不重复
                 undelivered[]        未能发送的日期
                 quadrant             q1-q4，用户手动
                 steps[{title,done}]
                 done completedOn completion{date,time,via}
                 completedDates[] completions{}   长期任务按天记
                 source               来源原话

state.habits[]   id name frequency
                 state               进行中|暂停|放下（休眠是算出来的）
                 minVersion          缩小后的最小可行版本
                 logs[{date}]

state.insights[]  id quote title body tags[] sourceId date via useForProfile
                  quote 必须是来源原话的子串，永不改写
                  body  助手整理过（或用户改过）的正文；老数据可能为空，取 quote 兜底
                  tags 自由多选，最多 3 个
                  useForProfile 勾上即画像确认，接后端时落成 confirmed 的 profile_item

state.progress[] {date, time?, text, taskId, via}
state.snippets[] {id, date, time?, text, summary?, chatId?, source?}  日记片段（id 是经验条目的引用目标）
state.chat[]     {role, text, channel, time, id?}
state.diary[]    {id, date, text}
state.dayOrder   {"YYYY-MM-DD": [taskId,…]}  待办页人工排过的顺序，按天
```

## 6. 还没做的部分

### 接口（A 侧的主要工作）

- 调 `/api/v1/turns` 提交输入、`/api/v1/tasks` 读清单、`/api/v1/corrections` 提交纠正、`/api/v1/events/{id}` 查来源。
- **身份校验**：现在完全没有。方案是微信网页授权（`snsapi_base` 静默授权）→ 后端用 code 换 OpenID → 签发自己的会话 cookie。只有第一次打开走一遍，之后靠 cookie，用户无感。**不能用 URL 参数里的 user_id 当身份**，改一个字符就能看别人的日记。
- **澄清分支没有显示位置**：解析失败时后端返回「原话已保存 + 一个澄清问题」，聊天页现在没有对应的样式。
- **纠正没有做成事件**：现在详情页直接覆盖字段。PRD 和 SPEC 都要求纠正追加一条记录、保留历史，删除只能标记撤销。

### 关于「验收里哪些是 A 的活」

这个问题前面讨论过，结论记在这里：

- **回执文案是后端生成的**（SPEC 6.3 的 `reply_text`）。A 只负责显示，并区分三种结果：recorded / duplicate / clarification_required。
- **提醒的三种状态也是后端判断的**（只有它知道微信窗口有没有关），但**必须显示给用户看**——PRD 4.3「H5 保留提醒记录供用户查看」，冒烟用例 D 要求「已保存、已发送和未能发送分别显示，用户查看时能理解发生了什么」。这不是测试产物。
- 一句话：**判断归后端，显示归前端。** 位置这一版都留好了。

### 其他缺口

- 存疑项的「待确认区」（PRD 2.4：24 小时未回复进 H5 待确认区）没做。
- 习惯打卡的数量和部分完成（PRD 3.6 `amount` / `partial`）界面上没有。
- 语音入口在公众号侧，H5 只复用转写结果。

### 下一版提案

经验本**这一版已经做了**（含自由标签、搜索、助手整理、保存感受后的建议卡），决定经过见**第 3 节末「感想、经验总结与日记的归属」**。`docs/insight-notes-v2.md` 里的固定五类 topic 方案已被推翻，那份文件只作讨论留档，**实现以本文为准**。

## 7. 渠道与部署（本轮确认的结论）

这部分影响前端能不能被试用者打开，记在这里备查。

- **个人主体订阅号没有客服消息接口权限**（调用报 48001），所以走**公众平台接口测试号**。
- **测试号的网页授权域名可以直接填 IP，不需要备案**（正式服务号才强制 ICP 备案、不支持 IP）。这一条来自多个开发者记录，**没有官方文档明文，第一天必须真机验一遍**。
- 建议服务器用**香港轻量应用服务器**（腾讯云/阿里云），免备案即买即用，CN2 线路国内延迟 30–60 ms。不建议 Vercel：大陆访问不稳、微信回调要求 5 秒内返回、Serverless 没有持久磁盘，队友的 Python 后端要改造。
- 国内节点未备案时 80/443 会被拦截，备案要 10–20 个工作日，来不及。
- 不建议用队友的旧电脑做试用期服务器：内网穿透地址会变、电脑一睡眠服务就挂，提醒发不出会被记成「未能发送」，污染验收数据。
- 测试号只能测试，关注人数有上限（有说法是约 100，**未核实**），不能正式发布；长期上线要主体认证的服务号。

试用排期：11-25（第 11 天）先放 2 人，11-27（第 13 天）再放 5 人。

## 8. 资源怎么来的

要重新生成插画、图标或字体子集时的记录。

- 字体子集：`pyftsubset ChillRoundM.ttf --text="<用到的字>" --layout-features='*'`，再用 fontTools 改 name 表为 LD Round，存 woff2。
- 图标和小狗：手写 SVG 路径 → rough.js 的 `generator().path()` 逐条抖动（roughness 0.5–0.6，`preserveVertices: true`），填充色保留在干净路径上，抖动只作用于描边。脚本是 `art/rough.mjs`，用法 `node art/rough.mjs 源.svg 输出.svg <roughness> <seed>`，只处理带 `data-rough` 的 `<g>`。
- 后加的三个图标（麦克风 / 皇冠 / 玫瑰）同一套做法，源文件 `art/icons2_src.svg`、`art/rose_src.svg`。前两个和导航图标一样用 `currentColor`；**皇冠和玫瑰是写死颜色的**（皇冠 `#f0c04a`/`#c2922b`，玫瑰 `#e98b9a`/`#a3485a` + 叶子 `#7aa75c`），因为它们是徽章不是图标，不跟文字颜色走。徽章在 20–26px 下也要认得出，改形状之后务必缩到那个尺寸看一眼。
- 插画：**现在用的四张是产品负责人给的手绘稿**，只做了缩放（宽 700px）和转 WebP（quality 82–86）；logo 另外用 PIL 洪水填充抠掉白底存成透明 PNG 再转 WebP。之前那套 SVG + `feTurbulence` / `feDisplacementMap` 的水彩滤镜做法已经弃用，留个记录：它画不出真正的手绘质感，当时就建议换人画或生图，这一轮换掉了。
- 所有资源最终以 base64 内嵌进 HTML，没有外链。

## 9. 改动时的工作方式建议

这个文件是单文件、没有构建系统的原型，手改容易出错。前面几轮是这样做的，效果还行：

1. 把当前文件复制一份当 base，写一个 Python 脚本做精确字符串替换，每处替换断言出现次数（不是 1 次就报错退出）。这样改了 40 多处也不会悄悄改错地方。
2. 用 headless Chrome + puppeteer 跑一遍功能测试：保存、拖动、展开、打卡、校验，顺便抓 `pageerror` 和 console error。
3. 桌面 1280 和手机 390 两个宽度各截一次图，肉眼看一遍。

测试脚本和构建脚本不在交付文件里，需要的话可以重写，上面三步是关键。
